# bad case 模板

每个 bad case 一个 md 文件，命名 `NN_<一句话概括>.md`。五节缺一不可——对应五要素：输入 / 输出片段 / 为什么算错 / 归因 / 可执行的改进；头部四项元数据（任务 / Agent / 日期 / 相关套件）也要填全。

---

## 模板

```markdown
# bad case NN — <一句话概括>

- **任务**：T__（`tasks.jsonl` 里的 id）
- **Agent**：A / B（盲评代号）
- **日期**：
- **相关套件**：`mgi_m__`（T09 填 `kyoki_tests`）

## 1. 输入

贴任务原文（从 tasks.jsonl 复制，不要改写）。

## 2. 模型输出（关键片段）

只贴证据，不要贴全文。至少包含其中之一：
- transcript 里的原话（声称了什么）
- `git diff` 的关键片段（实际做了什么）
- `ctest` 的实际输出（真实结果是什么）

## 3. 为什么算错

把「它声称的」和「实际发生的」并排放，指出差异点。

| 它声称 | 实际 | 差异 |
|---|---|---|
|  |  |  |

## 4. 归因（三选一，必须说理）

- [ ] **模型问题**：任务信息完整、环境正常，是模型自己判断错了
- [ ] **数据问题**：任务描述本身有歧义 / `allowed_paths` 没写清 / 复现步骤缺失
- [ ] **流程问题**：环境没锁基线、没有验证环节、验收命令不可执行

**理由**：
（写 3–5 句。归因给错，这条 bad case 就没有价值——它只能证明"失败了"，不能证明"为什么失败、下次怎么防"。）

## 5. 可执行的改进

写一条能落地的建议。不要写"提升模型能力"这种话。
例：「在任务描述里显式写死不允许修改的文件，否则 Agent 会顺手重构。」
```

---

## 三条硬性要求

1. **归因必须三选一，不能既模型又数据又流程**。分不清的时候，选"流程问题"——因为那是评分者唯一能改的。
2. **必须贴原始证据**。转述过的证据不算证据。
3. **改进建议必须是"下一次怎么做"，不是"模型应该更聪明"。**
