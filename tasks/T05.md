# T05 · 内容指纹（SHA-256 流式）

> feature · medium · `mgi_m15`（22 断言）· 基线 `612ff4e^` → gold `612ff4e`

## 1. 任务原文

> 用户报告：同一首歌只是换了个文件夹或者改了文件名，系统就当成新文件重新导入一遍，库里出现两条记录。请在导入时计算文件内容指纹（流式读取，大文件不能一次读进内存），文件移动后用指纹确认是同一个文件而不是新文件；已经入库的历史数据要能补算指纹。

## 3. Gold 答案分析

**改动规模**：555 行新增 / 9 行删除，11 个文件。核心 `Hashing.cpp` + `ScanService.cpp` +78 行。

**核心设计决策**：

1. **SHA-256 流式实现，零第三方依赖**。不引 OpenSSL 不引 mbedtls——`core/Hashing` 自实现 SHA-256，分块读取。理由：依赖少一层，构建链少一个炸点（这个项目的哲学是所有第三方依赖都要 vendor 或自实现）。
2. **512MB 上限**。超过 512MB 的文件不即时计算指纹，标记后台补算。避免一个超大文件卡住整个扫描。
3. **移动匹配二级确认**。文件移动后不是"路径变了就当新文件"——先按指纹找候选，**指纹一致才确认是同一个文件**（`verified:1, hash_confirmed:1`），指纹不一致直接排除。路径只是线索，内容才是身份。
4. **backfillHashes 幂等补算**。已入库的历史数据可以重复执行补算而不会出错——同一个文件补算一百次，结果一样。
5. **FileRow 补 contentHash 水合**。所有返回文件行的查询方法都要带上指纹字段，保证下游（对账、匹配）随时可用。

## 4. 难点与易错点

- **流式读取**：最容易犯的错是整个文件读进内存再算——大文件直接 OOM。必须分块（通常 64KB 或 1MB 一块）。
- **移动 vs 复制**：用户把文件从 A 复制到 B（两份都在）和从 A 移动到 B（只有一份）是不同的。指纹只能识别"内容相同"，不能区分用户意图。
- **补算的时机**：backfill 放在扫描主流程里会拖慢扫描；放后台又怕永远轮不到。gold 的解法是幂等设计，跑几次都不出错，时机就灵活了。

## 5. 面试讲解点

**考什么**：这条任务的本质是"**路径不是身份，内容才是**"。文件可以改名、移动、复制，但只要字节流一样，它就是同一个东西。考 Agent 能不能把"身份"和"位置"分开。

**被追问"为什么不用 MD5"**：
> MD5 有已知碰撞攻击，做内容指纹不够安全。SHA-256 在这个场景没有性能瓶颈（磁盘 IO 才是瓶颈，哈希计算比读盘快得多），选它是为了碰撞概率可以忽略。而且自实现没有第三方依赖，构建链少一个炸点。
