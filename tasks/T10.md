# T10 · Bangumi Provider（外部 API 集成）

> feature · hard · `mgi_m20`（26 断言）· 基线 `8fa8dee^` → gold `8fa8dee`

## 1. 任务原文

> 用户要接入一个外部番剧数据库：输入作品名能搜到候选条目（中文名、原名、别名都要能命中），选中候选后能取回详情并落库，取回的原始响应要留档便于以后核对。另外要求这个外部源不能污染核心域模型——接入前后，其它模块的代码不需要跟着改。

## 3. Gold 答案分析

**改动规模**：663 行新增 / 1 行删除，10 个文件。核心 `Providers.cpp` +120 行、`WinHttpTransport.cpp` +97 行。

**核心设计决策**：

1. **搜索用 POST 不是 GET**。Bangumi API v0 的搜索接口只接受 POST（body 带关键词、类型、分页）。Agent 容易想当然用 GET 拼 URL，直接被服务端拒绝。
2. **`HttpTransport::post` + `IProvider::postWithRetry`**。HTTP POST 能力加在传输层（WinHTTP），重试逻辑加在 Provider 接口层——关注点分离。
3. **中文名优先**（`name_cn` 优先于原名）。用户搜的是中文名，匹配和展示都应该优先中文。
4. **零侵入核心**（GATE-4）。接入 Bangumi 后核心域模型零改动——没有 bgm 专属表、没有 bgm 专属字段。跨域验证走统一管线：anime 实体 → 候选 → 人工确认 → `external_link CONFIRMED`。
5. **原始响应留档**（D010 统一管线）。每次 API 调用的原始 JSON 存下来，以后出了问题可以回查"当时服务器返回的到底是什么"。

**实网冒烟**：`live_smoke_bangumi` 真的调了 bgm.tv，返回 5 个候选并落库——不是 mock。

## 4. 难点与易错点

- **POST vs GET**：Bangumi 的搜索是 POST，跟大多数 REST 直觉相反。不看文档直接写 GET 会被拒。
- **重试策略**：公共 API 有速率限制（≤1 req/s）。无限制重试会被封。
- **零侵入的诱惑**：图省事在核心实体表里加个 `bgm_id` 字段，一时方便，但每接一个外部源就加一个字段，表结构会爆炸。gold 用统一的 `external_link` 表。
- **实网测试的不确定性**：bgm.tv 可能不可用或返回变化。测试用 FakeTransport 注入网络行为（M8 模式），实网冒烟单独跑。

## 5. 面试讲解点

**考什么**：接外部 API 不是"调个接口就完事"，而是**传输层抽象、重试策略、数据落库、原始留档、核心零侵入**五件事同时要考虑到。

**被追问"实网冒烟和单元测试怎么配合"**：
> 单元测试用 FakeTransport 注入假的网络行为，保证确定性——任何时间任何机器跑结果一样。实网冒烟单独跑，验证"真的连得上、真的返回了真实数据"。两者不互相替代：只有单元测试你不知道 API 真的通不通，只有实网冒烟你的测试就依赖外部服务可用性。
