# T11 · 泛媒体四域与跨媒体关系

> feature · hard · `mgi_m23_m25`（30 断言）· 基线 `983cb73^` → gold `983cb73`

## 1. 任务原文

> 用户现在不只管理音乐，还要把漫画、小说、动画、游戏四类也纳进来，而且四类之间要能建立跨媒体关系（比如同一部作品的漫画版和动画版互相关联）。要求扩展数据模型时不改变已有音乐数据的语义，已有的查询和统计不能因此失效，老库升级上来不能丢数据。

## 3. Gold 答案分析

**改动规模**：361 行新增 / 4 行删除，6 个文件。**实现几乎全在 SQL 迁移文件里**（`006_media_domains.sql` 87 行）。

**核心设计决策**：

1. **只加不改**。迁移 006 新增 10 张明细表 + 8 条关系类型行，**不改任何已有表**。音乐数据的 schema 一个字没动。这是"老库升级不丢数据"的保证。
2. **统一实体创建入口** `ensureTypedEntity`。漫画、小说、动画、游戏不走各自的建表逻辑，全走同一个入口——类型是参数，不是分支。
3. **关系类型是运行时目录行，不是编译时枚举**。新增关系类型（如 `based_on` 扩展到跨媒体）只需往目录表插一行，`QueryEngine` 零改动。GATE-5 验证的就是这个：**新增域不需要修改旧 Domain 的代码**。
4. **跨媒体关系复用通用 Relationship**。漫画版 ↔ 动画版不是特殊关系类型，就是普通的 `based_on`——两端类型不同而已。六域（音乐/漫画/小说/动画/游戏/广播剧）在同一张图里贯通。

## 4. 难点与易错点

- **改动范围极小但影响面极大**：只改 3 个文件，但涉及 6 个域的实体模型。Agent 容易认为"加四张表很简单"，忽略了"不改旧表"和"关系运行时扩展"这两个约束。
- **跨媒体关系 vs 同媒体关系**：同一部作品的漫画和动画之间的关系，跟同一专辑里两首歌的关系，是同一套机制吗？gold 的回答是"是"——都用通用 Relationship，只是两端实体类型不同。
- **旧数据兼容**：迁移前后已有音乐数据的语义完全不变，已有查询和统计不受影响。

## 5. 面试讲解点

**考什么**：这条任务考**开放-封闭原则**的数据库版。能不能做到"对扩展开放（加四个新域），对修改封闭（不改旧表旧代码）"。

**被追问"为什么不给每种媒体建独立表"**：
> 建了。但只建明细表（各域特有的字段），公共部分（实体、关系、状态、标签）全部复用。如果给每种媒体建完整的独立体系，六个域就有六套关系表、六套状态机、六套标签系统——跨媒体关系根本没法做。统一底座 + 域明细表是唯一可扩展的结构。
