# T01 · 单写者写入队列

> feature · medium · `mgi_m16`（15 断言）· 基线 `6352f6d^` → gold `6352f6d`

## 1. 任务原文

> 用户报告：在多个界面操作同时写数据库时，偶发“database is locked”导致写入失败，而且失败后数据只写进去一半，需要手工修复。请实现一个单写者写入队列：所有写操作排队后串行执行，支持优先级、支持取消排队中的任务、事务失败要整体回滚并把错误传给调用方、程序退出时队列要能排空。

## 3. Gold 答案分析

**改动规模**：452 行新增 / 1 行删除，6 个文件。核心实现 `WriteQueue.cpp` 151 行。

**核心设计决策**（从 commit message 与 diff 提炼）：

1. **单写者而非加锁**。SQLite 是单文件数据库，多连接并发写必然撞 `SQLITE_BUSY`；与其到处加锁，不如**结构上保证只有一个写者**——所有写操作进队列，由一个专用执行器串行消费。
2. **事务是回滚单位**。每个任务内部是完整事务：失败就整体回滚，不存在"写了一半"。这直接回应任务里的"数据只写进去一半"。
3. **取消只作用于排队中的任务**。已经开始执行的任务不能取消——取消了反而制造半截状态。这是最容易被忽略的边界。
4. **异常必须传到调用方**。队列吞掉异常等于"静默失败"，调用方会以为成功了。异常要沿原路返回。
5. **排空语义**。程序退出时队列里剩余的任务要执行完，不能丢——否则用户最后一次操作可能没落库。

## 4. 难点与易错点

- **取消语义**：Agent 最容易实现成"随时可取消"，结果把正在执行的事务也掐了，正好制造出任务要解决的那种半截状态。
- **优先级与公平性**：高优先级任务插队会不会饿死普通任务？gold 的做法是**优先级只在排队阶段生效**，执行器仍是 FIFO 消费，不抢占。
- **排空 vs 取消的冲突**：用户点了取消又立刻关程序，是先排空还是响应取消？需要明确语义。

## 5. 面试讲解点

**考什么**：并发写冲突是 SQLite 单文件库的经典问题。这条任务考 Agent 能不能选**结构解法**（单写者）而不是**局部补丁**（各处 try-catch 锁错误）。

**被追问"为什么不用多连接 + WAL"**：
> WAL 只解决读写并发，不解决写写并发——写者之间还是互斥的。而单写者队列顺带拿到了三个免费的好处：事务边界清晰、取消语义可控、退出排空可保证。锁方案一个都给不了。
