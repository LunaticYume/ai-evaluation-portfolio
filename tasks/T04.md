## 1. 任务原文

> 用户报告：扫描一个大目录时界面整个卡死，既看不到进度，也没法中途取消，只能强杀进程。请把扫描改成异步：界面要能实时显示进度，能暂停，能取消，而且取消之后不能留下半截状态（临时文件、未完成的事务、残留的线程）。

## 3. Gold 答案分析

**改动规模**：705 行新增 / 7 行删除，13 个文件。**全部 18 条任务里最大的一条。**

**核心设计决策**：

1. **协作式取消，不是抢占式**。`ScanControl` 注入扫描循环，在**检查点**（阶段边界 / 每 25 个文件）轮询取消标志。扫描线程不会被强制杀掉——它自己看到标志后有序退出。这是"不留半截状态"的根本保证。
2. **取消 → 会话标记 CANCELLED**。`finishSessionIfRunning` 做幂等兜底：不管扫描在哪一步被取消，会话状态都收敛到 CANCELLED，该批次事务回滚，不留残留。
3. **专用线程 + 独立连接**。`AsyncScanController` 起专用扫描线程，用**独立的数据库连接**——暂停期间主线程可以正常读库（独立连接不冲突），取消时也不用等主线程的连接释放。
4. **GUI 不阻塞**。扫描期间界面照常响应：进度状态栏、取消按钮、完成自动刷新。

**最重的测试**：3000 个文件扫到一半取消，重新扫描能续完且不留重复实体。

## 4. 难点与易错点

- **取消的粒度**：每文件检查一次太频繁（性能），每阶段检查一次太迟钝（点了取消要等很久）。gold 用"每 25 文件"折中。
- **暂停 vs 取消**：暂停要能从断点恢复（会话状态保留），取消要回滚干净（会话状态作废）。两个语义完全不同，Agent 容易混。
- **线程残留**：取消后线程对象不释放，下次扫描起新线程 → 线程泄漏。gold 的独立连接 + 明确生命周期管理是防这个的。
- **事务边界**：扫描是分批事务，取消时当前批次回滚、已提交批次保留——"已扫完的保留，没扫完的丢弃"。

## 5. 面试讲解点

**考什么**：异步改造不是"加个线程"就完事，而是**取消语义、事务边界、线程生命周期**三个问题同时要答对。这条任务考的是 Agent 能不能处理"半路退出"这个最难的场景。

**被追问"为什么是协作式不是抢占式"**：
> 抢占式取消（杀线程）在持有锁或事务中间被掐断时，留下的就是任务里说的那种"半截状态"。协作式取消让线程自己走到安全点再退出，代价是响应慢一点点（最多 25 个文件的延迟），换来的是"取消后一定干净"这个保证。在数据安全优先的系统里，这个交换永远值得。
