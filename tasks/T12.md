# T12 · ViewEngine 视图/工作簿引擎

> feature · medium · `mgi_m6`（36 断言）· 基线 `1ac9664^` → gold `1ac9664`

## 1. 任务原文

> 用户需要自定义工作簿视图：能把不同字段自由组合成一张可排序、可筛选的表格，视图要能保存、改名、删除，切换视图后表格内容立刻跟着变。数据量上千条时切换不能卡，也不能每次切换都全表重扫。

## 3. Gold 答案分析

**改动规模**：1032 行新增 / 13 行删除，11 个文件。测试占 342 行。

**核心设计决策**：

1. **自实现极简 JSON 解析器**（`core/Json`，RFC8259 子集，264 行）。视图定义是 JSON 字符串，需要一个解析器。不引第三方库——依赖控制哲学。
2. **视图定义 → QuerySpec 编译执行**。用户定义的视图不是每次切换时逐行解释，而是**编译成 QuerySpec 后交给已有的 QueryEngine 执行**。复用而不是重写——这是"切换不卡"的关键。
3. **可见性三源合并**：`changed_or_marked = 变更 ∪ 标记 ∪ pinned`。一个条目之所以出现在视图里，可能是因为它变了、被标记了、或被用户钉住了。三个来源都要支持。
4. **变更信号补齐**。`setStatus / removeStatusAssignment` 返回"是否实际变化"，StateEngine 的用户写入 / 扫描物理变化 / 文件删除与复活都会触发 `derived_changed_at`——视图引擎靠这个信号知道"该刷新了"。

## 4. 难点与易错点

- **JSON 解析器范围**：RFC8259 全集很大。gold 只实现子集（对象、数组、字符串、数字、布尔、null），不实现 Unicode 转义、科学计数法等。够用且不臃肿。
- **复用 vs 重写**：Agent 容易为视图引擎写一套新的查询逻辑，而不是编译成已有的 QuerySpec。重写的代价是两套查询逻辑可能不一致。
- **刷新时机**：视图什么时候该刷新？gold 用 `derived_changed_at` 信号驱动——不是定时轮询，不是每次切换都重算。

## 5. 面试讲解点

**考什么**：这条任务考**编译思维**——把用户的高级描述（视图定义 JSON）编译成底层执行计划（QuerySpec），而不是写一个解释器每次逐行执行。

**被追问"为什么自己写 JSON 解析器"**：
> 这个项目只有一处需要 JSON（视图定义），引一个第三方 JSON 库进来意味着多一层依赖、多一个构建目标、多一个可能的版本冲突。264 行自实现覆盖 RFC8259 子集，够用、可控、零依赖。这不是重新造轮子，是**控制依赖面**。
