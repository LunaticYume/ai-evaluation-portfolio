# T16 · 外部接入层解耦与原始载荷留档

> feature · hard · `mgi_m8`（36 断言）· 基线 `d45eafc^` → gold `d45eafc`

## 1. 任务原文

> 用户报告：外部数据源接进来以后有三个问题——① 每换一个数据源就要改传输层代码，测试的时候还会真的往外发请求；② 接口偶尔超时或者返回非 200，程序直接抛异常，整批导入就断了；③ 出了问题想核对「当时服务器到底返回了什么」，结果什么都没存下来。
>
> 请重做接入层：Provider 接口与 HTTP 传输解耦，测试能注入假传输、不发真实请求；超时 / 重试 / 退避可配置，非 200 不当致命错误；每次调用的原始响应按「来源 + 时间」留档。两个真实源（MusicBrainz、封面图库）都要走这一套。

## 3. Gold 答案分析

**改动规模**：本次 commit 涉及 15 个文件，其中实现 9 个（含 4 个头文件），另有 3 个测试文件与 1 个一次性补丁脚本（**不在** allowed_paths 内，Agent 不应碰）。

**核心设计决策**：

1. **传输层是接口，不是实现**。`HttpTransport` 抽成纯接口（GET / POST / 超时 / 状态码 / 原始 body），`WinHttpTransport` 只是一份实现。测试注入 `FakeTransport` 就能在不联网的前提下造出 404、500、超时、畸形 JSON 各种响应。
2. **失败分层**。网络错误、非 200、解析失败是三类不同的事：前两类可重试（带退避），第三类直接判该候选无效但不中断整批。**整批导入不该因为一条坏数据全断**。
3. **原始载荷按来源+时间落库**。每次调用把原始响应写进 `IndexDatabase`，带 `provider` 与 `fetched_at`。理由不是"备份"，而是**事后可对账**——三个月后用户说"这条信息不对"，你能翻出当时服务器原话，而不是猜。
4. **两个真实源走同一套**。MusicBrainz（元数据）+ 封面图库 CAA（图片）能力不同，但都实现同一个 `IProvider`，`ProviderService` 只按接口编排，不写 `if (provider == "musicbrainz")`。
5. **重试有上限**。公共 API 有速率限制，无节制重试会被封 IP；退避与上限必须可配。

## 4. 难点与易错点

- **把"解耦"做成"多一层转发"**：常见错法是加一个 `ProviderManager` 但内部仍然 `new WinHttpTransport`，测试还是发真请求。判据是**测试能不能注入假传输**。
- **非 200 当异常抛**：这是任务里"整批中断"的根因。正确处理是**记录并跳过**，同时把失败计入结果摘要。
- **原始载荷存哪**：存文件系统会随部署漂移，存库才可查可对账。但也**不能存进核心实体表**——它是旁路审计数据。
- **重试与幂等**：重试的是"取数据"，不是"落库"。落库必须幂等，否则重试会把同一条候选写成两条。
- **超时值拍脑袋**：需要一个默认值 + 可配，且**超时必须真的传给 WinHTTP**，不能只在接口上声明。

## 5. 面试讲解点

**考什么**：外部依赖是**不可控**的。这条任务考的是"把不可控挡在边界外"——三条边界：传输可替换（测试可控）、失败可分层（不炸整批）、载荷可追溯（事后可对账）。

**被追问"为什么不直接用 curl / 第三方 HTTP 库"**：

> 这个项目对第三方依赖的规矩是能自实现就自实现、必须引就 vendor。HTTP 只用到 GET/POST/超时/状态码这一个子集，WinHTTP 是系统自带的，就不需要再引一层。更重要的是**接口是我定的**：`HttpTransport` 只有 5 个方法，测试写一个 Fake 就 30 行，换成任何库都能接。

**被追问"原始响应留档会不会把库撑爆"**：

> 会，所以它是旁路数据、不是核心域数据：单独的表、可以按时间清理、不参与任何查询路径。这条设计的价值不在存储，在于**出问题时唯一的证据链**——数据质量岗位上，"当时对方返回了什么"是判定责任的唯一依据。

**和 T10 的区别（别讲混）**：

> T10 是接入一个**具体**外部源（番剧库），考点是"零侵入核心域"——不许为它加专属字段。T16 是重做**接入层本身**，考点是"传输可替换 + 失败分层 + 载荷留档"。一个是接一个源，一个是修一条管道。
