## 3. Gold 答案分析

**改动规模**：386 行新增 / 12 行删除，10 个文件。测试占 215 行。

**核心设计决策**：

1. **实时 SQL 聚合，不保存统计副本表**。这是项目 D005 哲学的直接延伸——"派生状态实时计算、不落库"。统计数字是从源表现算的，库里没有一份"统计结果表"。**为什么不缓存？因为缓存了就有脏数据风险**：源表改了统计表没更新，用户看到的就是错的。
2. **`StatisticsEngine` 六种聚合**：实体类型计数、状态分布、标签排行、重复组数、缺失数、总实体数。覆盖用户要的"数量、分布、排行榜"。
3. **`IndexDatabase::queryRows` 通用只读行集**。统计查询和诊断查询共用这个入口，不各写各的——查询逻辑只有一处。
4. **顺带修正了 mgi_m3 的迁移版本断言**（4→6）——说明作者在做统计时发现了一个旧断言过时了，顺手修了。这种"发现就修"的习惯本身就是评测想看的。

## 4. 难点与易错点

- **实时 vs 缓存的权衡**：数据量大时实时 SQL 聚合可能慢。gold 的选择是"先正确，再优化"——SQLite 的索引做好，万级数据量实时聚合完全够用。Agent 容易一上来就建缓存表，引入脏数据风险。
- **排行榜的分页**："按艺人排行"可能有几百个艺人，全量返回拖慢 UI。需要 LIMIT + 分页。
- **重复组的统计口径**：重复组数 ≠ 重复文件数。三个文件互为重复是"1 组"不是"3 个"。

## 5. 面试讲解点

**考什么**：这条任务考"**什么时候不该优化**"。直觉是"统计要缓存才快"，但缓存引入一致性问题。gold 的选择是先保证正确性，用索引让实时查询足够快——这是工程判断，不是算法题。

**被追问"数据量大怎么办"**：
> 这个系统的目标场景是个人媒体库，量级在几万到十几万条。SQLite 有索引的情况下，GROUP BY 聚合在这个量级是毫秒级。如果真到了百万级，再加缓存——但加缓存的前提是**缓存可重建**，即"删掉缓存表重新跑一遍统计能还原"。可重建的缓存才安全。
