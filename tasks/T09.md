# T09 · 红基线归因（诊断）

> diagnosis · hard · `kyoki_tests` · 基线 `2520cb2`（KyoKiNexus 开发态）

> ⚠️ 这条任务是**诊断题**，不是功能题。正确答案不是"修好"，而是"**说清楚为什么全红**"。

## 1. 任务原文

> 接手一个别人的项目：跑测试发现整套测试是红的。几十个测试套件几乎全部失败，每个套件的失败数量都不少，报错信息看上去各不相同但气质很像。项目负责人要求"把所有测试修绿"。请定位为什么测试全红，说明根因是什么、你怎么验证这个判断，并给出最小修复路径。注意：不要逐个套件去改断言或改实现——先回答"为什么会全红"。

## 2. 验收标准

| 项 | 标准 |
|---|---|
| 命令 | `ctest --test-dir build-eval --output-on-failure`（需 Qt PATH，复现步骤见 `runs/README.md` §5） |
| 通过 | **不改任何源码或测试文件**；给出根因结论 + 验证方式 |
| 红线 | 改了任何文件 → fail；逐个套件改断言 → fail；结论不指向单一根因 → partial 以下 |

### 正确归因路径

1. 跑一次全量 ctest，收集失败分布
2. 发现**失败形态高度同质**：每个套件固定 `2 passed`（initTestCase / cleanupTestCase）+ `N failed`
3. 追踪失败点：全部卡在 `initWorkEditionAssetRepos(m_conn, &m_error)` 或 `workRepo.initialize()` 返回 FALSE
4. 报错信息统一：`datatype mismatch Unable to fetch row`
5. 结论：**数据库 schema 与代码期望的版本不匹配**（仓储初始化阶段的迁移未执行或版本落后），是**单一根因**，不是几十个独立缺陷
6. 修复路径：修迁移或测试夹具初始化，**一处修完全绿**

### 错误归因路径（任何一个都算 fail）

- 逐个套件看断言失败 → 改断言让它过
- 认为"每个套件各有各的问题" → 分别修
- 不看输出分布就猜原因
- 宣称"修好了"但没有复跑验证

## 3. 事实基础

这条任务不是编的。以下事实经过两次独立实跑确认：

| 时间 | 环境 | 结果 |
|---|---|---|
| 2026-10-13 | 旧构建目录 | `exit=31`，FAIL |
| 2026-10-23 | 全新构建（`build-eval`，119/119 编译通过） | `exit=31`，FAIL |

失败分布（82 个套件日志，`<CACHE_DIR>/kyoki-*.txt`）：

- 大量套件呈现 **2 passed + N failed** 的同一形态
- 失败点统一为 `initWorkEditionAssetRepos()` 或 `workRepo.initialize()` 返回 FALSE
- 报错文本统一为 `datatype mismatch Unable to fetch row`

**项目自己的 README 记载"22 套件 100% passed"是 v1.0.1 发布基线，与当前开发态不同。** 这意味着：接手时不能信文档，只能信实跑。

## 4. 难点与易错点

- **心理压力**：几十个套件全红的视觉冲击很大，直觉反应是"这项目烂透了"。正确反应是"这么一致的失败，根因只有一个"。
- **stdout 误导**：直接跑 `kyoki_tests.exe` 只能看到 4 行输出（测试主程序把明细写到了独立日志文件 `kyoki-<suite>.txt`）。只看 stdout 会以为"只失败了几个"，实际 82 个文件里藏着完整的失败分布。
- **修 vs 诊断的冲动**：项目负责人说"修绿"，但任务要求"先回答为什么"。忍住不动手改代码是最难的部分。

## 5. 面试讲解点

**考什么**：这是全部 18 条任务里**唯一不考写代码的**。它考的是**诊断能力**——面对一个全红的基线，能不能先停下来分析失败分布，而不是急着修。

**被追问"你怎么知道是单一根因"**：
> 因为失败形态完全一致。每个套件都是前两个测试通过（initTestCase 和 cleanupTestCase，不涉及数据库），中间的测试全挂（都要初始化仓储）。如果每个套件各有各的问题，失败分布不会这么整齐。这个同质性本身就是"单一根因"的证据——你只需要找到所有失败共同卡在哪一行。

**被追问"你遇到过吗"**：
> 遇到过。这个项目的早期环境就出现过同类问题——同一套代码换一台机器全部失败，退出码统一 `0xc0000139`，根因是 Qt 运行库不在 PATH。那次是环境问题，这次是 schema 问题，但诊断方法一样：**先看失败分布的同质性，再追共同入口**。
