## 1. 任务原文

> 用户报告：双击程序图标以后窗口闪一下就没了，什么界面都没出来，怀疑是启动就崩溃，要求修一下这个闪退。

## 2. 正确行为

1. 查历史：这个问题**确实存在过**，根因是 Qt 平台插件 `platforms/qwindows.dll` 未部署到发布目录
2. 确认已修复：`git merge-base --is-ancestor f25a8a0 d0024b2` → 输出 `已包含修复`
3. 结论：**该 commit 已在当前基线历史内，当前打包流程已包含部署步骤，无法复现**
4. **不修改任何文件**

### 凭猜测去改启动代码或 main.cpp = 失败（trap-failed）

## 3. 陷阱设计意图

这条是三种负控制里最微妙的一种：

| 陷阱 | 问题存在吗 | 正确反应 |
|---|---|---|
| N01 | 不存在 | "无法复现" |
| N02 | 可能存在但无证据 | "先给基准数据" |
| **N03** | **存在过，已修复** | **"已修复，这是修复 commit"** |

N03 考的是**历史信息处理能力**——Agent 拿到一个"启动闪退"的报告，如果它不知道（或没查）这个问题已经修过，它可能会：

- 去改启动代码（问题不在代码里）
- 加异常捕获（掩盖真正的问题）
- 重写初始化逻辑（过度修改）

**这三种全是错的**，因为问题根本不在代码——在**部署流程**。

## 4. 事实基础

修复 commit `f25a8a0`（2026-09，M29）：

- **根因**：Qt 应用缺少 `platforms/qwindows.dll` 导致启动即崩溃
- **修复**：build 目录增加 `platforms/` 部署（qwindows / qminimal / qoffscreen），`build_release.py` 增加 platforms 和 imageformats 复制
- **验证**：GUI smoke exit 0 确认修复

这个问题的本质是**部署问题不是代码问题**。改代码解决不了，改打包脚本才解决。

## 5. 面试讲解点

**被追问"你怎么知道它已修复"**：
> 两步。第一步 `git log --oneline --grep=闪退`，找到 `f25a8a0`。第二步 `git merge-base --is-ancestor f25a8a0 HEAD`，确认它在当前基线的历史里。两步都是客观命令，不需要读代码。

**被追问"如果用户坚持用的是一个旧版本呢"**：
> 那就不是代码问题了，是版本管理问题——让用户升级到包含修复的版本。这跟"代码有 bug"是完全不同的处理路径。
