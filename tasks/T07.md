## 3. Gold 答案分析

**改动规模**：1057 行新增 / 29 行删除，19 个文件。测试占 326 行。

**核心设计决策**：

1. **`VACUUM INTO` 做在线备份**。不是文件复制，不是逐表导出——VACUUM INTO 是 SQLite 原生的在线备份方式：产出一个压缩后的一致快照，**备份期间不锁库**，用户可以正常读写。这是"不能挡住正常使用"的唯一正确解法。
2. **GATE-7：备份 → 新库恢复 → 全量一致**。备份好不好不是靠"文件生成了"判断的，是靠**恢复出来的新库和原库数据完全一致**判断的。实体、关系、标签、状态、Claim、视图、版本——七类数据全部对账。
3. **`integrityCheck`**：备份完成后跑 SQLite 自带的 `PRAGMA integrity_check`，验证备份文件没有损坏。
4. **CSV 导出带 UTF-8 BOM**。不带 BOM 的 CSV 用 Excel 打开中文全乱码——这是真实用户场景的细节，不是炫技。

## 4. 难点与易错点

- **备份方式选错**：`文件复制`（数据库正被写时复制出来的是不一致的）和 `逐表 INSERT`（慢且容易漏表）都是常见错误。VACUUM INTO 是唯一既在线又一致的选择。
- **恢复验证被跳过**：很多 Agent 会实现备份但不验证恢复。GATE-7 的价值就在这里——**备份不可恢复的备份等于没有备份**。
- **JSON vs CSV 的语义差异**：JSON 保留完整结构（嵌套关系、数组），CSV 是扁平的（一行一个实体）。导出 CSV 时多对多关系怎么表达是个设计决策。

## 5. 面试讲解点

**考什么**：备份是"平时没用、出事救命"的功能。这条任务考 Agent 能不能做到**备份可恢复**——不是"生成了一个文件"就叫备份完成，而是"这个文件能恢复出完整的数据"才算完成。

**被追问"为什么不用文件复制"**：
> 数据库文件在被写入时直接复制，复制出来的可能是不一致状态——正在写一半的事务被你抄走了。VACUUM INTO 是 SQLite 提供的在线一致快照，备份期间正常读写不受影响。这是"在线备份不锁库"的标准答案。
