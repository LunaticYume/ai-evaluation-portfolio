# T14 · 六维状态机 + 标签继承

> feature · medium · `mgi_m4`（56 断言）· 基线 `be262c7^` → gold `be262c7`

## 1. 任务原文

> 用户要求每个作品能同时标记多个维度的状态（比如获取状态、阅读状态、收藏状态），各维度互不干扰；每个维度内部只能按合法路径流转，非法流转要被拒绝并说明原因；每次流转都要留下记录（谁改的、什么时候、改成什么）。另外标签要能继承——给文件夹打标签，里面的文件自动带上。

## 3. Gold 答案分析

**改动规模**：1707 行新增 / 50 行删除，16 个文件。**全部 18 条任务里改动文件最多的一条。**

**核心设计决策**：

1. **六维权限矩阵**。状态有六个维度（ACQUISITION、PROGRESS、COLLECTION、MANUAL 等），每个维度有不同的写入权限。**扫描只能写 PHYSICAL 维**——扫描器没有资格碰用户的获取状态或收藏状态。这是"扫描不覆盖用户状态"（T-STATE-04）的结构性保证。
2. **状态机合法性校验**。每个维度有自己的 `allowed_next` 表，非法转换（如 ACQUIRED → PLANNED）被拒绝并说明原因。不是"先改了再说"，是"改之前就拦"。
3. **人工标记不入状态机**。MANUAL 维度的标记是自由的，不受状态机约束——用户想标什么标什么，不触发任何自动转换。
4. **有效状态 = 用户显式值 ?? 派生值**。用户设了就用用户的，没设就用派生的。派生值是实时计算的（folder → release → track 逐层聚合），不落库——避免脏数据被固化。
5. **派生缓存 + 信号驱动**。派生值缓存到 `derived_state_cache` 表，但只存缓存不存真相；源数据变了发 `derived_changed_at` 信号，下游刷新。
6. **标签继承用递归 CTE**。文件夹标签继承靠 SQL 递归 CTE 查询实时计算，不把继承结果落库——文件夹改了标签，里面的文件立刻跟着变。

## 4. 难点与易错点

- **状态机表的设计**：每个维度的合法转换路径不同，需要逐维度定义。Agent 容易用一个通用状态机套所有维度，结果"获取状态"和"收藏状态"用同一套流转规则。
- **派生值落库的诱惑**：把派生值算好存到表里，查询快。但一旦源数据变了忘了更新缓存，用户看到的就是错的。gold 宁可每次算也不冒脏数据的风险。
- **扫描不覆盖用户状态**：这是整个项目最重要的一条不变量。T-STATE-04 的断言是"用户设了 ACQUIRED 之后重扫，ACQUIRED 不变"——守的是"人工优先"。
- **递归 CTE 的性能**：文件夹层级深时递归查询可能慢。但个人媒体库的文件夹层级通常不超过 5-6 层，性能不是瓶颈。

## 5. 面试讲解点

**考什么**：这条任务考**状态管理的边界感**——谁有资格改什么状态、状态从哪来、派生值怎么算。它不是"写个 enum 加几个 if"那么简单。

**被追问"为什么扫描只能写 PHYSICAL"**：
> 因为扫描器是自动程序，它不应该覆盖人的判断。用户在界面上点了"已收藏"，下次扫描不能因为文件状态变了就把收藏状态改了。物理状态（文件在不在、改没改名）是扫描器的天职；获取状态、收藏状态是用户的天职。这就是六维权限矩阵存在的理由。

**被追问"T-STATE-04 是什么"**：
> 这是整个项目最重要的一条断言：用户把获取状态设为"已获得"之后重新扫描，获取状态必须不变。它守的不是一个功能，是一条原则——**人工优先于自动**。如果扫描能覆盖用户状态，那用户就不敢用扫描了。
