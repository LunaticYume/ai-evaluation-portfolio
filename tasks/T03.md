# T03 · 文件系统对账

> feature · medium · `mgi_m18`（16 断言）· 基线 `89a3c90^` → gold `89a3c90`

## 1. 任务原文

> 用户报告：他习惯在文件管理器里直接删文件、移动文件、改文件名，结果库里的记录和磁盘实际状态对不上——有的记录指向的路径已经不存在，有的文件在库里没有对应记录。请实现一次对账：把磁盘现状和库记录比对，输出一份报告，至少包含重复文件、失效路径、未识别文件三类。

## 3. Gold 答案分析

**改动规模**：477 行新增 / 133 行删除，10 个文件。核心 `ScanService.cpp` +48 行。

**核心设计决策**：

1. **报告输出八类，不是三类**：`added / removed / moved / renamed / changed / duplicates / stalePaths / unknown`。任务只要求三类，但 gold 覆盖完整——因为对账的价值就在于"所有不一致都看得见"，只报三类等于留了盲区。
2. **报告只读**。对账结果是一份报告，**不产生任何写动作**。物理文件被删了，库里的逻辑实体**不删**（物理/逻辑分离红线贯穿）——只在报告里标为 `stalePaths`。
3. **连续对账全净**：跑一次对账再跑一次，结果必须一致（零新增实体）——这是对账自身的幂等性断言。
4. **同内容复制识别**：同一首歌被复制到两个文件夹，对账要能识别出"内容相同的两份"，而不是当成两个新文件。

## 4. 难点与易错点

- **物理删除 ≠ 逻辑删除**：用户在文件管理器删了文件，库里的作品记录不能跟着没——这是整个项目最核心的不变量之一（路径非身份）。Agent 容易在对账时顺手"清理"逻辑实体，直接踩红线。
- **移动/改名 vs 删除+新增**：文件从 A 目录移到 B 目录，是"移动"不是"删除 A + 新增 B"。区分要靠内容指纹（T05）。
- **未识别文件**：磁盘上有但库里没有的，只列出、不自动导入。

## 5. 面试讲解点

**考什么**：对账是"**数据库记录** vs **磁盘现实**"的一致性检查。这条任务考 Agent 能不能守住"报告是只读的"这条边界——会写对账的很多，能忍住不顺手修复的很少。

**被追问"为什么不顺手修"**：
> 对账和修复是两个操作。对账的职责是"让人看见"，修复的职责是"经人批准后执行"。混在一起，用户还没看报告数据就被改了，等于把审计和执法合并了。Review Inbox 队列就是干这个的：先归集，再人工复核。
