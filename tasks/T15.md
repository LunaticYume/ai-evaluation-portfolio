# T15 · 多对多关系与查询引擎

> feature · hard · `mgi_m5`（50 断言）· 基线 `da63340^` → gold `da63340`

## 1. 任务原文

> 用户报告：一首歌经常同时属于多张专辑、有多个演唱者，现在系统按一对一存，导致查一首歌只能看到一个专辑、查一个歌手只能看到一首歌。要求改成多对多关系，并且能按关系反查（查某张专辑有哪些歌、某个歌手参与了哪些作品），查询结果不能有重复，删除一侧时另一侧的关系要跟着清理但不能误删实体。

## 3. Gold 答案分析

**改动规模**：1252 行新增 / 14 行删除，9 个文件。核心 `QueryEngine.cpp` 395 行 + `IndexDatabase.cpp` +277 行。

**核心设计决策**：

1. **QueryEngine 是唯一数据入口**。所有查询（表格视图、图视图、搜索）都经过 QueryEngine——不允许多个模块各自写 SQL。这保证"查询结果不能有重复"只有一处要管。
2. **QuerySpec 过滤器**。查询条件（有效状态、标签继承、关系传递、FTS、文件夹、release_track、外部链接）统一抽象为 QuerySpec，编译后执行。
3. **多对多的去重规则**。`addRelationship` 做端点类型校验 + 纯重复行拒绝（同属性同序拒绝），但"一首歌有多个演唱者"这种合法多行不拒。区分"真重复"和"合法多值"。
4. **统一图视图 `graphEdgesOf`**。关系行 + 派生边（D008/D007/R205）统一成一张图，`neighbors` 支持 1/2/N 跳边过滤展开 + multiHop 无向多跳。
5. **手动录入服务**（R206）。Work / Release / ReleaseTrack / recording.work 挂接——不依赖扫描也能建关系。

## 4. 难点与易错点

- **多对多 vs 单外键**：这是这个项目里 AI 曾经犯过的真实错误——把多对多简化成单外键（一个字段存一个 ID）。查询能跑，但"一首歌属于多张专辑"就丢了。这是任务设计的核心考点。
- **反查的性能**："查某张专辑有哪些歌"容易，"查某个歌手参与了哪些作品"需要多表 JOIN。索引设计要跟上。
- **删除的级联边界**：删一首歌要清理它的关系行，但不能删专辑实体。这个边界画错了就是级联误删。
- **FTS 组合搜索**：全文搜索不只是搜歌名——还要搜演唱者名、专辑名、文件夹路径。

## 5. 面试讲解点

**考什么**：这条任务考**关系建模的成熟度**。一对一用外键谁都，多对多要用中间表、要处理去重、要支持反查、要控制级联——这才是真实世界的数据关系。

**被追问"AI 犯过什么错"**：
> 这个项目开发过程中，AI 曾经把"一首歌多个演唱者"设计成单外键——recording 表加一个 `artist_id` 字段。这样每个录音只能有一个演唱者，多个就丢了。我审查时挡回去了，要求改成关系表（中间表），一行一个"录音-演唱者"对。这就是为什么这个项目现在有多对多查询能力。
