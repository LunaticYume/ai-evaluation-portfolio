## 1. 任务原文

> 用户报告：库用久了会出现三类问题但系统发现不了——①同一个作品被导入了多次（重复实体）②关系表里指向了已经不存在的实体（孤儿关系）③同一个字段有多个来源给了不同值（冲突）。现在没有任何报表能看见这些，只能人工翻。请实现一份数据质量报告，能分别列出重复、孤儿、冲突三类问题，并对重复实体给出合并建议。

## 3. Gold 答案分析

**改动规模**：534 行新增 / 164 行删除，9 个文件。核心 `DataQuality.cpp` 101 行。

**核心设计决策**：

1. **三类问题分开报告，不混**。重复（规范化同名 + 同内容指纹强候选）、孤儿（关系指向不存在的实体）、冲突（同字段多来源不同值）各自独立列出，因为它们的处理方式完全不同：重复要合并、孤儿要清理、冲突要人工裁决。
2. **`suggestKeep` 只建议、不执行**。合并建议里"保留哪个"由**挂接最多者**启发式给出，但**合并方向由用户显式确认**——系统绝不自动合并。这是整个项目的"人工优先"铁律的直接体现。
3. **合并复用 M9 匹配引擎**（T08），不重新发明合并逻辑。
4. **SQL 收敛到 database 层**。对账和质量查询全部下沉到 `IndexDatabase`，不在业务层散落 SQL——保证一致性检查的逻辑有唯一入口。

## 4. 难点与易错点

- **重复的判定标准**：同名 ≠ 重复（可能有同名不同曲）。gold 用"规范化同名 + 内容指纹"两道门槛，Agent 容易只用文件名判重，误报一堆。
- **孤儿清理的边界**：孤儿关系要"列出"而不是"直接删"。直接删就违反了"报告只读"的原则——**报告是给人看的，不是给程序执行的**。
- **冲突的值来源**：需要能追溯每个值从哪个 Provider 来，否则冲突报告只是"两个值不一样"，无法裁决。

## 5. 面试讲解点

**考什么**：数据质量不是"发现问题"，而是"**把问题变成人可处理的清单**"。三类问题的处理路径完全不同，能分清这一点说明理解了数据治理的本质。

**被追问"为什么不自动合并"**：
> 自动合并错了是不可逆的——把两首不同的歌合并成一首，引用迁移之后想拆开比不合并还难。启发式建议 + 人工确认的成本很低，错误成本是零。这在生产环境叫"人在环路"（human-in-the-loop）。
