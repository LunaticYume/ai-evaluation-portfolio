# T13 · Plugin SDK 与 CSV 导出示例

> feature · medium · `mgi_m10_m11`（21 断言）· 基线 `0140956^` → gold `0140956`

## 1. 任务原文

> 用户希望第三方能写插件来扩展程序能力：插件要有清单文件声明名字、版本和所需权限，程序加载时必须校验权限，越权的插件不给加载；插件之间要互相隔离，一个插件出错不能拖垮主程序。同时提供一个官方示例插件，能把库里的数据导出成 CSV。

## 3. Gold 答案分析

**改动规模**：602 行新增 / 63 行删除，13 个文件。

**核心设计决策**：

1. **窄 API 面**（`PluginHost`）。插件能调用的 API 是一个**刻意收窄的接口**——不是把整个数据库句柄暴露给插件，而是只暴露"读实体列表、读标签、导出"这几个操作。窄 API = 可控的攻击面。
2. **版本化 manifest + 权限校验**。每个插件必须有清单文件声明名字、版本、所需权限。加载时校验：版本不兼容拒绝、权限越界拒绝。
3. **Registry 异常隔离**。插件抛异常不会让主程序崩溃——Registry 捕获并隔离，其它插件和主程序继续运行。
4. **CSV Exporter 经 Service API**。官方示例插件不走内部后门，跟第三方插件走完全相同的 API——证明"窄 API 够用"。
5. **CSV 带 UTF-8 BOM**。跟 T07 的备份导出同一原因：Excel 兼容性。

## 4. 难点与易错点

- **API 面太宽**：Agent 容易把内部接口直接暴露给插件——一时方便，但等于把安全边界拆了。窄 API 面是设计决策，不是偷懒。
- **权限声明 vs 权限执行**：manifest 里声明了权限，但运行时真的拦吗？gold 在 Registry 层做运行时校验，不是只看声明。
- **示例插件的代表性**：CSV Exporter 不只是"一个例子"，它证明窄 API 足以支撑真实功能。如果官方示例都要走后门，那窄 API 就是失败的。

## 5. 面试讲解点

**考什么**：插件系统的核心不是"让别人能写插件"，而是"**让别人只能在你的边界内写插件**"。这条任务考的是安全边界设计。

**被追问"为什么不用动态库加载"**：
> 动态库（DLL）加载的插件跟主程序在同一进程里，一个插件崩溃就拖垮整个程序。这个项目选择了更保守的方案：插件通过 SDK 的窄 API 通信，Registry 做异常隔离。代价是插件能力受限，换来的是主程序永远不被插件拖垮。
